# 型号归一口径修正报告（甲方更正：前导零 = 不同尺寸）

> 目标：修正**产品/报价的型号归一口径**，并重新产出可用的候选清单。
> 结论先行：**归一化本身从未删除前导零**（唯一一处「折叠数字」在变体清单的分组指纹里，已修）；
> **上一轮导入的 1444 条产品与 2582 条报价没有发生尺寸合并，无需数据修正**；
> 需要改的是「129 组疑似同产品不同写法」的**分类**，以及三处**子串容错匹配缺少数字守卫**的隐患。

## 一、归一化审计结论（最高风险项）

### 1.1 甲方更正的口径

> 「**0-GPN 和 00-GPN 是同一型号的不同尺寸**」

落地为三条硬规则：

1. 前导零 / 数字位数差异 = 不同尺寸 = 不同产品，**绝不合并**；
2. 归一化只做「空格 / 全角半角 / 大小写 / 标点」层面，**数字部分（含前导零、位数、后缀号数）原样保留、逐字符比较**；
3. 「是不是同一个产品型号」= `normalizeToken` 相同 **且** `digitSignature`（数字指纹）相同。

新增的唯一权威判定（`apps/api/src/ai/table-parser.service.ts`）：

| 函数 | 作用 |
| --- | --- |
| `digitSignature(s)` | 按出现顺序抽数字段并用 `-` 连接：`0-GPN`→`"0"`、`00-GPN`→`"00"`、`1-1-101`→`"1-1-101"`、`111-01`→`"111-01"` |
| `sameProductModel(a,b)` | 文本归一相同 **且** 数字指纹相同 |
| `productIdentityKey(s)` | 去重键 = 文本归一 + `#` + 数字指纹 |
| `sameProductDigits(a,b)` | 子串容错匹配的前置守卫（只比数字部分） |

工具侧（`tools/ziliao/lib/ziliao-extract.mjs`）提供**逐字符同口径**的实现，避免两套口径漂移。

### 1.2 审计发现（4 处，均已修正）

| # | 位置 | 问题 | 修正 |
| --- | --- | --- | --- |
| ① | `tools/ziliao/lib/ziliao-extract.mjs` `modelFingerprint` | **确实折叠了前导零**：`t.replace(/(^\|[^0-9])0+(\d)/g,'$1$2')` 把 `00-GPN`/`000-GPN` 折成 `0-GPN`，是 129 组变体清单把三种尺寸当成「同一产品不同写法」的**根因** | 删除折叠；另立 `variantGroupFingerprint`（**只用于把同族写法聚到一起供人工分类**，注释明令禁止用于合并/去重/取价） |
| ② | `apps/api/src/ai/order-parser.service.ts`（识单产品匹配）<br>`apps/api/src/orders/orders.service.ts`（落草稿产品匹配） | **无约束双向子串匹配**：`normName('1-101割嘴00#').includes('1-101')` 成立 → 计划单的 `1-101` 会错落到 **另一个尺寸** `1-101 割嘴 00#` 的档案上（价格/工艺全错） | 保留子串容错（描述/品牌前缀差异仍可命中），**加数字守卫** `sameProductDigits` |
| ③ | `apps/api/src/quotes/quote-pricing.ts` `matchQuoteProduct`<br>`apps/api/src/quotes/quotes.service.ts` `quoteKey` / 产品匹配 | 按名称取价只比 `normalizeToken`；标点删除会让 `1-1-101` 与 `111-01` 假相等；报价导入唯一键同理 | 取价加数字指纹双重相等；报价唯一键改用 `productIdentityKey` |
| ④ | `apps/api/src/master-data/master-import.service.ts`（建档判重 / 表内查重 / 提交时二次查重） | 产品判重只按名称归一 → 标点不同但数字分段不同的型号会被判成「已存在」而**漏建档** | 产品键改用 `productIdentityKey`（客户仍按名称归一，行为不变） |

**关键澄清**：`normalizeToken` 本身**从来没有**删除前导零或折叠数字位（它只处理空格/全角半角/大小写/标点）。
唯一的数字折叠就在 ① 那个只服务于「变体清单分组」的指纹函数里，而 `products_variants.csv` **没有任何消费方**
（`import_products_cloud.mjs` 走服务端建档判重），所以它只污染了**清单的分类描述**，没有污染数据。

## 二、变体清单重新分类（A 类 / B 类）

分组口径不变（仍用宽松指纹把同族写法聚到一起），**分类**改为看数字指纹：
组内数字指纹**全部一致** → A 类；出现 **≥2 种** → B 类。

| 分类 | 组数 | 条数 | 含义与动作 |
| --- | --- | --- | --- |
| **A 类·纯文本差异** | **5 组** | **10 条** | 仅空格/全角半角/大小写/标点/描述性后缀 → **可合并候选**，附建议标准名（脚本仍**不自动合并**） |
| **B 类·数字/尺寸差异** | **124 组** | **576 条** | 前导零、数字位、后缀号数不同 → **同型号不同尺寸，不合并，各自建档** |
| 合计 | **129 组** | **586 条** | 与上一轮条数完全对齐，便于逐组复核 |

另附**更实用的 A 类清单**：把 B 类组内「同一尺寸的多种写法」也捞出来（那些确实是纯文本差异、可合并）：

| 附加清单 | 簇数 | 条数 |
| --- | --- | --- |
| A 类·可合并候选子簇（同一数字指纹 + ≥2 种写法） | **50 簇** | **104 条** |

产出文件（已落到 `tools/ziliao/`）：

* `products_variants.csv` —— 全量 586 条，新增列：`差异类别`、`数字指纹（逐字符）`、`尺寸分组号（B类用）`；
* `products_variants_A_文本差异.csv` —— A 类可合并候选（附建议合并后的标准名）；
* `products_variants_B_尺寸差异.csv` —— B 类，逐行标注「同型号不同尺寸，不合并，各自建档」。

典型例子（这次修正的核心）：

## 三、型号对照候选（用于解锁缺价，但安全优先）

**口径（宁缺勿错）**：

1. **数字部分（含前导零、位数、后缀号数）逐字符完全一致** —— `digitSignature` 相等是硬门槛，不满足一律不出候选；
2. 只允许「描述 / 品牌前缀差异」：归一写法必须互为**子串**（如计划单 `1-1-101` ↔ 合同 `Victor 乙炔割嘴 1-1-101`）；
3. **不做无约束子串匹配去凑覆盖率**；服务端取价仍是**精确口径**（没有改成子串匹配）；
4. 脚本**只出候选供人工确认**：不写库、不改报价、不自动应用对照关系。

产出 `tools/ziliao/model_alias_candidates.csv`（列含：计划单写法、候选合同写法、候选来源客户、候选单价/日期、来源文件、**匹配置信度**、**数字部分是否完全一致（全部为「是」）**）。

| 指标 | 数值 |
| --- | --- |
| 计划单产品行 | 1604 |
| 已按「归一写法 + 数字指纹完全相同」命中 | 82 |
| 缺价 | **1522 行 / 340 种写法** |
| 有对照候选（同客户或跨客户） | **94 种 / 971 行** |
| —— 其中仅跨客户有候选（需甲方裁定是否可作通用价） | 79 种 |
| —— 其中同客户有多个候选（需人工挑一个） | 58 种 |
| 无候选 | 246 种 / 551 行 |
| **因数字指纹不一致被主动拒绝**的子串相似对 | **11290 对** |
| 候选条数（含「无候选」占位行） | **497 条** |

置信度规则（可解释）：同客户 + 唯一候选 = 高；同客户 + 多候选 = 中；只有跨客户候选 = 低。

**这次修正救回的典型误配**（旧口径直接给了错价线索，新口径拒绝）：

| 计划单写法 | 旧口径给的「疑似价源」 | 新口径 |
| --- | --- | --- |
| `0-GPN` | `victor 丙烷割嘴 GPN－00#（刻字：内嘴上00-GPN）@8.50` | **无候选**（`0` ≠ `00`，是不同尺寸 → 拒绝） |
| `00-1-101` | `割嘴 #00-1-101 仿包装 @12.80` | **保留候选**（数字部分完全一致） |
| `1-1-101`（86 行缺价） | `Victor 乙炔割嘴 1-1-101 @13.20` | **保留候选**（数字部分完全一致，跨客户待裁定） |

## 六、遗留与建议

1. **B 类 576 条的建档**：它们是「同型号不同尺寸」，需要甲方按尺寸确认后各自建档（当前库里已各自在档，无需动作；
   但产品类型 1173 条仍是 `tbd` 待人工确认）。
2. **A 类 5 组 / 10 条 + 子簇 50 簇 / 104 条**只是**可合并候选**，脚本不自动合并；
   建议人工确认后用标准名维护，避免下次导入又出现两种写法。
3. **对照候选 497 条必须人工确认**后才可落地为同客户报价（或经甲方裁定作为**通用价**）；
   跨客户的 79 种涉及「安宝合同价 → 嵊州海田计划单」，属于业务决定，脚本不代裁。
4. **服务端取价仍是精确口径**（归一相等 + 数字指纹相等），**没有**为凑覆盖率放宽为子串匹配；
   1264/1522 行缺价的解锁路径是「人工确认对照关系 → 做成报价」，而不是放宽匹配。
5. **回归护栏**：`product-identity.spec.ts` 是这条口径的守门员 —— 以后任何往归一化里加「数字折叠」的改动都会红掉。
